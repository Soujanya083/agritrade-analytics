# Limitations, authenticity notes and viva preparation

This document exists so the project can be defended honestly. Nothing here is hidden elsewhere in the code.

## 1. What is real, simulated, or rule-based

| Component | Status |
|---|---|
| Accounts, JWT auth, listings, bidding, deals, notifications | **Real** (tested with Jest + in-memory MongoDB in CI) |
| Price/demand forecasting, backtesting, ARIMA, RandomForest + SHAP | **Real ML code** running on whatever data is in MongoDB |
| Buyer segmentation (RFM + K-Means), anomaly detection | **Real ML code** |
| Real market forecasts (Analytics -> *Real market data*) | **Real data, real evaluation** - AGMARKNET history you import (`docs/REAL_DATA.md`). Empty until you import it |
| Marketplace data in the demo | **SYNTHETIC.** `seed_data.py` generates listings, bids and sales with a built-in seasonal pattern. Backtest accuracy measured on it shows the code works, **not** that it predicts real markets |
| Mandi prices | **Real** from data.gov.in AGMARKNET when `DATAGOVIN_*` is set. Without it, a small **saved snapshot (onion only)** is used and labelled `cached_snapshot` |
| Net-profit "best market" | Real mandi prices minus **flat-rate transport/storage assumptions** (disclosed in the UI) |
| Chatbot: price/demand/where-to-sell answers | **Rule-based intent matching → real analytics functions.** No LLM, no hardcoded answers |
| Chatbot: general farming answers | **LLM**, only if `LLM_*` is configured; labelled "general AI answer - not from your data". Without a key it says so |
| Companion-planting guide | **Static curated data** (31 crops), labelled research-backed vs traditional. Not generated by AI at runtime |
| Crop photos | Real Pexels photos when `PEXELS_API_KEY` is set and a verified match is found; otherwise a labelled drawn icon |
| OTP verification | **Demo mode** - the OTP is returned by the API because no SMS/email provider exists |
| UPI payment | **Trust-based**: the buyer presses "I have paid". Razorpay (when configured) is verified by signature |

## 2. Known limitations (acknowledge these)

**Data science**
- **Real-data section is only as good as what you import.** With less than ~2 years of history the seasonality is flagged unreliable; with less than 120 days nothing is forecast.
- The forecast lab often concludes that *no model beats naive* for daily commodity prices. That is an honest result (price changes over 2 weeks are hard to predict), and the UI reports it instead of crowning a model.
- Significance uses a Holm correction across models, which lowers false wins but also lowers power on subtle structure.
- Conformal intervals describe past error on this series; shocks (weather, policy) will break them.
- (Fixed) The marketplace price series now uses the asking price, which is fixed when a listing is created, so later bids can no longer leak into training. Falls back to `currentBid` only when no asking prices exist, and says so.
- Models are fit on one marketplace's history; with little history they fall back to a linear trend, and the confidence label says so.
- The RandomForest target starts equal to `basePrice`, so "predict the asking price" is a strong baseline; the evaluation reports whether the model beats it.
- Isolation Forest labels roughly `contamination` % of records as outliers *by construction*; only records flagged by several detectors are "high confidence". The detectors were benchmarked on injected anomalies (docs/DS_METHODOLOGY.md): single detectors give many false alarms, and anomalies only ~10% above the asking price are mostly missed.
- The crop recommendation *score* is a weighted heuristic (weights are a documented judgment call). Its price term now measures buyer premium over asking price, not rupee level. It is not a profit forecast.
- SHAP explains the model's reading of the latest listing, which the model was trained on (in-sample); the response says so.
- Caching: invalidation detects new crops/bids/transactions and completed deliveries, not arbitrary in-place edits (the TTL is the backstop). Each worker process has its own cache.

**Security**
- (Fixed) The session no longer lives in `localStorage`: the short-lived access token (30 min) is held in memory only and a rotating **httpOnly refresh cookie** keeps users logged in; replaying a used cookie revokes the whole login chain. Remaining caveat: an XSS bug could still use the in-memory token while the page is open (for minutes, not 7 days). `/api/auth/*` uses a custom-header CSRF check.
- Login messages distinguish "user not found" from "wrong password" (usability over anti-enumeration).
- (Fixed when configured) With `EMAIL_PROVIDER` + key set, the OTP is e-mailed and never returned by the API. Without it the server runs in labelled **demo mode** (OTP echoed), which proves nothing; set the provider before any real use.
- The QR code for UPI is drawn by a third-party service (qrserver.com), which sees the payment link.
- If `CORS_ORIGINS` is unset the APIs accept any origin and cookie sessions are disabled in production (fail-closed). Set it when deployed. (Fixed: DELETE was missing from the allowed CORS methods, so deleting a listing from the deployed site would have been blocked by the browser.)

**Product**
- (Fixed) `GET /api/crops` is paginated (24 per page, max 60, server-side search/category filters) and photos are served from a cacheable `/api/crops/:id/image` URL instead of being embedded as base64 in every listing. Images still live in MongoDB; at larger scale they belong in object storage.
- Branding is inconsistent (AgriMarket / AgriTrade) in some UI text.
- Payments: no refunds, disputes or escrow.

## 4. Questions an examiner is likely to ask (and where the answer is)

- *Why Prophet, and what if there's little data?* Handles trend/seasonality with sparse data; <10 points falls back to linear regression (`price_prediction.py`).
- *How do you know the model is any good?* Rolling-origin backtest vs naive baseline; the UI reports if it fails to beat it (`model_evaluation.py`). Admit the demo data is synthetic.
- *Is there data leakage?* Chronological splits, lags built within each crop. Be ready to discuss the `currentBid` look-ahead above.
- *Why not predict with an LLM?* Numbers must come from auditable models; the LLM is limited to general text and cannot see or state prices.
- *How does the chatbot avoid hallucinating?* Data questions never reach the LLM; the LLM prompt forbids marketplace figures; answers are labelled by source.
- *How is the analytics service secured?* Same JWT, verified with the shared secret, algorithm pinned, fails closed (`auth.py`).
- *Why in-memory cache, not Redis?* Single process/instance; Redis adds infrastructure with no benefit at this scale. State the multi-worker limitation.
- *How do you prevent two farmers/clicks accepting the same bid?* Atomic `findOneAndUpdate` claim on the crop (`server.js`, test in `hardening.test.js`).
- *What does K-Means segmentation add?* Groups buyers by recency/frequency/monetary value; labels come from cluster centroids; needs enough buyers or it returns 422.
- *What would you do next?* Real OTP/SMS provider, escrowed payments, httpOnly cookie auth, object storage for images, real (non-synthetic) historical data, per-crop seasonal models.

## 5. Extra viva questions for the data-science part
- *Why MASE, not just RMSE?* It scales error by the naive one-day change, so it is comparable across commodities and 1.0 means "as good as naive".
- *Why a Diebold-Mariano test?* Lower average error on a few test points can be luck; DM tests whether the difference is reliable, with a variance estimate that allows for overlapping windows.
- *Why a Holm correction?* Several models are compared to naive; without it, the chance that one wins by luck is much higher than 10%. Measured: 4/40 false wins before, 0/40 after, on random walks.
- *What are conformal intervals?* Intervals sized from the model's own past out-of-sample errors per forecast day; they need no distribution assumption, and the page reports their measured coverage.
- *What if the real data is missing?* The section says so and the summary falls back to marketplace data with a synthetic-data warning and capped confidence.
- *Where could leakage come from?* Models only receive values before each origin (tested with a spy model); seasonality is computed descriptively, not used as a feature.

## 6. The data-science story in one paragraph (for the viva)
"We forecast real mandi prices with a model comparison that is evaluated like research, not like a demo: rolling-origin backtests, a significance test corrected for testing many models, conformal intervals whose coverage we measure, and tests that tell us *why* a model wins or not. We validated each method on simulated data with known answers - for example, random walks almost never produce a false winner and real trends do. We found and fixed several flaws along the way, including look-ahead in the price series, zero-width fake intervals, a segmentation captured by one large buyer, and a score that favoured expensive crops. Where the data cannot support a claim, the system says so."
